# Contract design and implementation

Use this reference to add, modify, or fix EVM contracts. Translate the user's request into observable business rules before choosing an implementation. Address only the rules and boundaries affected by the change.

## Working in an existing project

- Use Foundry for new contract projects: business contracts in `src/`, `.t.sol` tests in `test/`, deployment and operations scripts in `script/`, and configuration in `foundry.toml`. Create only the files the task needs.
- Read compiler configuration, dependency locks, remappings, relevant contracts, tests, and deployment records to identify the actual Solidity and dependency versions.
- Preserve the project's Foundry, Hardhat, or other toolchain, existing modules, and error conventions. Do not bundle framework migrations, compiler upgrades, or package manager changes into a feature fix.
- Check the EVM version supported by the target chain. Successful local compilation does not prove that the chain supports the opcodes in the generated bytecode.
- When choosing a compiler, adding contracts, or preparing a release, check Solidity's known bugs against version ranges, optimizer, viaIR, evmVersion, and code conditions. Record relevant findings and their treatment. A version match alone does not establish exposure, and unrelated bugs do not justify migrating an existing project.
- Confirm constructor arguments, import paths, extension points, and error types against installed dependency source and matching documentation. The default documentation page may describe a different version.
- Prefer OpenZeppelin for standard tokens, access control, safe transfers, and signature verification. Reuse installed packages instead of copying their implementations. Select and pin compatible stable releases; Git installations should use release tags, avoiding development branches and implicit version drift. Do not edit dependency source to work around missing interfaces.

## Define business constraints first

Use a brief explanation or existing tests to answer the questions relevant to the task:

| Change involves | Establish before implementation |
| --- | --- |
| Administration | Who may call, who grants or revokes access, and how control transfers |
| Asset flows | Asset type, unit, recipient, accounting point, and state after failure |
| Minting or burning | Authorized actors, supply limits, and the relationship between balances and supply |
| One-time operations | The business identifier that prevents duplication and when it is consumed |
| Time or prices | Inclusive boundaries, data sources, invalidation conditions, and rounding direction |
| External integrations | Trusted return values, supported asset behavior, and possible callbacks |

For example, "only the minter may mint" also requires identifying the initial minter, behavior after revocation, and who administers that role. Do not expand a simple token task into pause, blocklist, tax, or proxy features.

## Permissions and asset accounting

- Reuse standard components compatible with the installed version. Choose a single administrator or multiple roles according to actual requirements; do not assume the deployer should retain every permission permanently.
- For a handover, establish the final owner/admin, role administrators, and their ability to accept control. Use a two-step transfer where applicable; see [deployment verification](deployment.md#permission-handover-and-operations) for role, multisig, and timelock acceptance checks.
- Enforce authorization at onchain entry points. Hiding a frontend button is not an access check; do not use `tx.origin` to determine business permissions.
- Define asset or share units and conservation relationships before implementing balance changes. Distinguish protocol accounting balances, token balances, native currency balances, and withdrawable amounts.
- When integrating external ERC20 tokens, use safe transfer wrappers compatible with the installed version and explicitly define support for fee-on-transfer or rebasing tokens. A safe transfer wrapper does not guarantee that the amount received equals the requested amount.
- Add balance-delta or other accounting only when the business supports those token behaviors. Otherwise enforce the boundary and document unsupported behavior.
- Specify rounding for division, fees, and share conversions. Check intermediate products, narrowing casts, and the assumptions behind `unchecked`. Use integer base units for onchain amounts.
- Do not identify assets by token name, symbol, or `decimals`; the contract address and chain ID identify the integration target.
- Add only the events and errors the business needs, allowing callers to distinguish rejection reasons. When changing existing signatures, check ABI consumers as well.

## External calls and execution limits

- Check permissions and inputs, complete necessary state updates, then interact. Treat token callbacks, NFT receiver callbacks, and cross-contract calls as potential transfers of control.
- Assess reentrancy protection across the full call path, including other functions and shared accounting state. Locking one entry point does not establish the safety of other paths.
- Check success flags for native currency transfers and low-level calls, and define failure behavior. A fixed gas allowance alone is not evidence that the recipient cannot reenter.
- Avoid operations that must iterate over an unbounded set of users. For batches, define limits or use pagination, individual claims, or another suitable business flow.
- External reads may fail or return unexpected values. Handle stale data, return values, and exceptions for dependencies involved in the task.

## Signature authorization, when relevant

- Establish the message type, signer, executor, beneficiary, and authorized action. An arbitrary signature must not grant arbitrary operation permissions.
- Match the client's structured encoding and signing domain. Check the chain ID, verifying contract, version, and other domain fields actually used.
- Implement nonce or business-identifier consumption, expiry, and replay constraints separately. EIP-712 encoding does not provide one-time consumption logic.
- Use a verification library compatible with the installed version instead of handwritten signature recovery. If contract wallets must be supported, verify the ERC-1271 path; recovering an EOA address is insufficient.
- For smart accounts or EIP-7702, read [smart accounts](smart-accounts.md). Do not treat `code.length == 0` or `msg.sender == tx.origin` as reliable proof of account type or absence of reentrancy. For login, see [wallet authentication](authentication.md).
- Test modified fields, mismatched domains, expiry, reuse, and incorrect signers. Do not use signature bytes themselves as the unique consumption identifier.

## Proxies and upgradeable contracts

- Identify the proxy type, implementation address, upgrade authority, initialization entry point, layout records, and existing upgrade tools. Distinguish proxy state from implementation-contract state.
- Preserve initialization and storage compatibility, including inheritance, field types and order, storage gaps, and namespaces. Appending fields is not sufficient proof for every layout.
- Check parent initialization, repeated execution, and implementation locking. Add initialization steps through the existing versioning mechanism without reinitializing existing state.
- Run the project's upgrade compatibility checks. Preserve the old implementation baseline and test important state before and after the upgrade. Do not assume storage compatibility across OpenZeppelin major versions.
- Ordinary fixes do not automatically authorize changing proxy patterns, migrating layouts, or executing onchain upgrades. When an upgrade is part of the task, prepare the implementation, validation, and deployment within its authorization; see [deployment and integration](deployment.md).

## Validation and delivery

Select checks using the [testing strategy](testing.md). Explain business behavior, interface or storage effects, and actual validation results. Identify checks that were not run.

For swaps, oracles, vaults, or lending, read [DeFi development](defi.md). When a change introduces a complex asset model or new protocol assumptions, state which assumptions remain unverified. Do not describe ordinary development results as an independent audit or a security guarantee.

## Official references, matched to the project version

- [OpenZeppelin Contracts](https://docs.openzeppelin.com/contracts/5.x): releases and standard components; use the matching major-version documentation for older projects.
- [OpenZeppelin Access Control](https://docs.openzeppelin.com/contracts/5.x/access-control): administrators, roles, and permission transfers.
- [Solidity Security Considerations](https://docs.soliditylang.org/en/latest/security-considerations.html): external calls, reentrancy, and gas limits.
- [Solidity Known Bugs](https://docs.soliditylang.org/en/latest/bugs.html): compiler issues by version, build settings, and affected code paths.
- [OpenZeppelin Cryptography](https://docs.openzeppelin.com/contracts/5.x/api/utils/cryptography): EIP-712, signature recovery, and contract-wallet verification interfaces.
- [Writing Upgradeable Contracts](https://docs.openzeppelin.com/upgrades-plugins/writing-upgradeable): initialization, storage layout, and upgrade compatibility.
